# Soak ACK and resize pipeline audit (2026-10-17)

This is a source-level failure-mode audit, not a root-cause finding for the failed soak. The observed run ended at `SOAK-0-196` after a five-second ACK wait; stream 0 had acknowledged token 195, emitted roughly 20 KiB / 85 output records afterward, and resize admission was repeatedly full near elapsed 984 seconds. A separate 20-minute run passed. Those observations do not identify which stage stopped making progress. The active two-hour run was not inspected.

## What the code establishes

`Command::Input` returning success means only that `InputWriter::try_write` put the byte vector into a bounded `sync_channel` (eight queued chunks, plus the worker's in-flight chunk). Its writer thread then calls `write_all` and `flush`; there is no completion acknowledgement back to the host command or soak harness. The API comment explicitly documents this distinction (`crates/session-host/src/input.rs:90-128`). Thus the harness's `writer_queue_admitted` marker is not proof that the child read `PING`.

The producer records `ping_received` only after its raw-tty read splits a complete newline-terminated command, writes the synthetic ACK bytes, and records `ack_write_completed` (`scripts/soak-pty.py:54-72, 73-104`). It then waits for `RELEASE` while continuing to poll stdin every 50 ms. The harness polls snapshots until the ACK is in a published frame, then sends RELEASE (`scripts/soak-pty.py:645-689`). Therefore a missing ACK in the frame is compatible with at least three states: input was admitted but not delivered/read; the child wrote ACK but the host has not yet published it; or snapshot/polling itself is failing/late. The child-side datagrams distinguish these states when received, but absence of a datagram is not proof of absence of the event because the sidechannel is best-effort UDP.

PTY output is read on a separate thread, but that thread synchronously sends `Action::Output` into an eight-entry channel (`crates/session-host/src/lib.rs:840-870`). If the actor stops draining, the reader eventually blocks in `send`, the PTY output buffer can fill, and the child can block in `write(1, ...)` before it returns to reading PING/RELEASE. This is bounded buffering, not dropped output.

The actor drains one action or a bounded 64 KiB output batch (up to a 250 μs coalescing window), then serially performs synchronous work before publishing a frame: journal append+`sync_all`, history append/commit+index `sync_all`, optional checkpoint publication, query-response admission, frame construction and snapshot replacement (`crates/session-host/src/lib.rs:910-943, 1202-1265`; `crates/storage/src/journal.rs:403-449`; `crates/session-host/src/history.rs:324-405`). Any of these synchronous filesystem/model steps can delay the actor. The journal and archive operations do not expose an interruption/deadline at these call sites, so the source alone cannot rule out a long filesystem wait. A resize accepted into the same actor channel can likewise wait behind output or this synchronous work; repeated QueueFull is evidence that the queue is occupied, not evidence of which operation occupies the actor.

There is one concrete actor-level wait cycle worth testing independently: after parsing a terminal query, the actor retains response bytes and gives their delivery priority over receiving the next PTY action. It attempts to queue response chunks (at most 16 KiB each); on `InputWriteError::Full`, it sleeps 2 ms and retries without draining the output channel (`crates/session-host/src/lib.rs:1097-1123`). If a child is blocked writing output while the response backlog fills the input writer queue, the actor can wait for the child to read responses while the child waits for the actor to drain output. The 16 MiB response limit bounds retained response bytes, but this priority loop itself has no progress timeout or output-drain escape. This is a plausible cycle, not an explanation of this incident: the synthetic producer pattern contains no intentional terminal query storm, and the available run facts do not establish that a query response was pending.

The actor also updates `View.sequence` and `View.frame` only after journal, history and checkpoint work succeeds. Its metrics are updated at publication time. Consequently a stale/unchanged snapshot during a stall cannot by itself distinguish “actor is blocked in persistence” from “actor is not receiving PTY bytes” or “child has not read input.”

## Minimal next diagnostic

Use a deterministic test PTY/child with explicit milestones around `PING` read, ACK write completion, and RELEASE read, while the host records monotonic timestamps for (a) input queue admission, (b) input worker write start/completion, and (c) actor stage entry/exit for journal append, history commit, checkpoint, query-response queueing, and frame publish. Keep the existing byte-free token index sidechannel; do not record terminal text or raw input. Bound samples to the current event/token and timeout artifact. This provides a direct stage boundary without changing ACK timeout, retries, pacing, or output semantics.

Add two focused regression tests:

1. A deliberately blocked `Write` fake proves that successful input admission can precede worker completion indefinitely while the actor remains independently serviceable. Then release the fake and assert exact FIFO completion. Existing `blocked_worker_has_bounded_nonblocking_fifo_admission` already tests queue saturation/FIFO, but it does not assert a caller-visible completion milestone because the API has none.
2. A child that emits a terminal query which creates a response, then writes enough output to fill the bounded PTY reader/actor path, should exercise the response-priority loop. Verify that output continues to be serviced while the response is pending, or establish a bounded, explicit degraded outcome. Do not infer this path ran in the soak unless query-response counters show it.

The first test clarifies the admission contract; the second proves or falsifies the only concrete host wait cycle identified here. For an actual soak timeout, correlate the existing child sidecar milestones with the proposed input-worker and actor-stage timestamps. A `ping_received` without `ack_write_completed` points to a producer write stall; both milestones without frame publication points downstream; no `ping_received` with a completed worker write points to PTY/child read progress; no worker completion points to the input writer. Because the sidechannel is lossy, absence needs corroboration from its sequence/drop accounting and process state.

## Limits

This audit does not establish a deadlock, disk fault, actor crash, or lost input. The current evidence is consistent with a transient filesystem delay, actor work backlog, child/PTY blocking, or an observation gap. The 20-minute pass demonstrates intermittency, not resolution. No 24-hour result or root cause is claimed.
