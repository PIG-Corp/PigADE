# Isolated Linux X11/XIM acceptance path — 0.0.1-dev

## Decision

The most direct candidate for an actual PigADE IME acceptance test is **X11/XIM in a private Xvfb server**, using Fcitx 5 with its Pinyin engine. The pinned GPUI backend contains an XIM handler, while the existing private Weston path does not implement the Wayland text-input protocol version GPUI uses. This is a proposed test, not evidence that IME composition or commit currently works.

During initial research, no provider, display server, input helper, or package was launched or downloaded. In the preparation slice below, package archives were downloaded, verified, and extracted; no package executable, display server, Fcitx process, application, or input helper was launched. An actual test must run only after a separately reviewed harness establishes the namespace and socket boundaries below. It must never fall back to the user's display or session bus.

## Why X11/XIM, not the current Weston path

PigADE's app currently pins GPUI source revision `322cd509dcccaee1f6bc44725d270598ae8171ad`. Its X11 `xim_handler` opens an XIM connection and handles preedit and committed text. The source calls `client.open("C")`, requests preedit callbacks, and does not consume caret/feedback metadata. The Wayland client binds `zwp_text_input_v3` and handles preedit, commit-string, and done events. These are the exact pinned sources: [GPUI XIM handler](https://github.com/zed-industries/zed/blob/322cd509dcccaee1f6bc44725d270598ae8171ad/crates/gpui_linux/src/linux/x11/xim_handler.rs) and [GPUI Wayland client](https://github.com/zed-industries/zed/blob/322cd509dcccaee1f6bc44725d270598ae8171ad/crates/gpui_linux/src/linux/wayland/client.rs).

Fcitx's Wayland documentation says Weston uses text-input-v1 on the application side and `zwp_input_method_v1` on the input-method side, and explicitly says Weston does not support text-input-v3. It describes Sway's text-input-v3 plus Fcitx `zwp_input_method_v2` path as partial. Therefore a successful Weston test cannot exercise GPUI's v3 client, and v2/v3 compatibility must not be inferred from a Weston handshake. See [Fcitx 5 on Wayland](https://fcitx-im.org/wiki/Using_Fcitx_5_on_Wayland/en).

There is one XIM-specific uncertainty to test: GPUI passes locale `C` in the XIM open request, whereas Fcitx's environment guidance says XIM needs an appropriate non-`C`/non-`POSIX` locale. Fcitx's `xcb-imdkit` implementation says it omits client-side locale checking, which may make this work, but does not prove that Fcitx's server registration and Unicode commit work with GPUI's request. Use a valid private process locale such as `C.utf8` or `en_US.utf8`, verify that the server advertises the requested XIM name, and treat preedit/commit as a runtime gate. Do not change GPUI locale negotiation or claim a fix based on protocol registration alone. References: [Fcitx environment variables](https://fcitx-im.org/wiki/Input_method_related_environment_variables/en), [xcb-imdkit](https://github.com/fcitx/xcb-imdkit).

## Package and license boundary

The installed machine has Fcitx 5.1.21 and `libxtst`, but no Xvfb, `fcitx5-chinese-addons`, or `libime`; the Chinese engine is not available from the installed Fcitx alone. This was read-only package inventory. The SDK prepared in this slice uses official signed Arch package archives and signatures, validates the installed Arch keyring and pinned archive hashes, rejects unsafe archive paths, and extracts into a fresh private test SDK. It does not run a package manager, install packages, execute package hooks, or edit system/user configuration. The existing `scripts/prepare-platform-sdk.py` remains unchanged; its 32 MiB download cap is too small for the current `libime` archive. The new X11 preparer instead bounds each archive at 60 MiB and the complete archive set at 90 MiB.

## Preparation result (2026-10-17)

The new `scripts/prepare-x11-ime-sdk.py` pins and verifies 13 Arch packages, their detached signatures, `.PKGINFO` identity and the signer primary fingerprint using the installed Arch keyring. It extracts into `/tmp/pigade-x11-ime-sdk-20261017/root/x11-ime-4efed4828ba785c5`; the complete package, signature, license, selected-path and dynamic-link records are in `/tmp/pigade-x11-ime-sdk-20261017/evidence/manifest.json`. The current extraction profile is `pinyin-punctuation-runtime-v2`. Its recorded status is `ready-for-isolated-review`, with no unresolved library names or symbols across 16 `ldd -r` checks. This confirms that the listed binaries/plugins resolve dynamic dependencies and relocations against the prepared SDK plus the current host `/usr`; it is not a full sysroot, runtime launch, plugin-load test, XTEST query, or proof of runtime ABI behavior.

The extracted package set is Xvfb 21.1.25-2, X server common 21.1.25-2, xauth 1.1.5-1, xkbcomp 1.5.0-1, setxkbmap 1.3.5-1, xkeyboard-config 2.48-1, libxtst 1.2.5-1, Fcitx 5.1.23-1, Chinese add-ons 5.1.15-2, libime 1.1.17-1, boost-libs 1.92.0-1, OpenCC 1.2.0-1 and marisa 0.3.1-1. The manifest preserves that package's declared dependency list and calls out the omission. This is a test fixture choice, not a claim that the full package is dependency-complete.

The preparer was exercised against the real pinned archives and the focused tests passed. It does not execute Xvfb, Fcitx, PigADE or the XTEST helper. The private SDK is ready for root review, not for user-facing “IME supported” claims. Its extracted Pinyin payload is GPL-2.0-or-later and must remain test-only unless product licensing is separately decided.

Fcitx documentation identifies `fcitx5-chinese-addons` as the package containing Pinyin and says engines must be explicitly configured. Its current zh_CN default profile lists Pinyin, but the test should create a fresh private profile with only the intended keyboard and Pinyin entries instead of inheriting machine configuration. See [Fcitx troubleshooting](https://fcitx-im.org/wiki/Troubleshooting) and [upstream zh_CN default profile](https://github.com/fcitx/fcitx5/blob/master/data/default/zh_CN). ## Isolated test topology and harness status

`scripts/isolated-ime-x11.py` implements this topology with plan-only behavior by default. This research/implementation slice did not pass `--run`, launch Xvfb/Fcitx/PigADE, or synthesize input. `--compile-helper PATH` only builds the reviewed fixed-sequence C helper and runs no display. A later authorized run must use a fresh private output directory outside the repository; its raw bounded process logs, host journal, and PPM captures remain in that private directory. Only curated hashes and conclusions belong in tracked evidence. The pre-commit PPM is a real private-root capture, but its visible preedit must be reviewed from the image; the harness does not machine-interpret screenshot pixels.

The harness uses the actual built PigADE app and existing private host IPC, plus these boundaries:

1. Verify a fresh, caller-owned private runtime root with restrictive permissions. Create separate private HOME, XDG config/cache/state/runtime directories and private DBus session. No host HOME, provider home, session/system D-Bus socket, X11/Wayland socket, compositor control socket, device input node, or desktop environment token may be mounted or inherited. Use a network namespace with no network interfaces; do not weaken it to accommodate an unexplained dependency.
2. The harness starts private Xvfb with `-displayfd`, `-nolisten tcp`, preloaded private Xauthority records, a fixed 1280×800×24 screen, and XTEST enabled. It never passes `-tst`. The cookie is generated in a fresh private runtime directory and is never placed in argv or evidence. It records the exact Xvfb PID/start identity, boot ID, display number and Unix-socket inode. The C helper checks socket inode/owner and `SO_PEERCRED` against the exact Xvfb PID on both Xlib and XCB connections, then checks `XTestQueryExtension`. It also checks XRes availability before any key event.
3. Fcitx runs in the same isolated namespaces with fresh HOME/XDG directories and a private D-Bus session. The environment sets private `DISPLAY`, matching `XAUTHORITY`, `XMODIFIERS=@im=fcitx`, and `LC_ALL=C.utf8`. A fresh profile names only the US keyboard and Pinyin. The harness supplies `LIBIME_MODEL_DIRS` pointing at the pinned SDK's `usr/lib/libime` model directory; the library contains this environment-variable name and `/usr/lib/libime` default path. This is a launch configuration to be validated by the future runtime probe, not evidence that the Pinyin engine loaded. After identifying the exact app window, the harness uses only the private-bus `fcitx5-remote` commands to select and activate Pinyin, then requires `-n` to report `pinyin`; it does not use shortcut keys for activation. The helper checks the active `XIM_SERVERS` owner via XRes local-client PID and requires the exact Fcitx process. `xcb-imdkit` constructs its XIM selection atom as `@server=<serverName>`; for the configured server name the harness requires `@server=fcitx`, not the XMODIFIERS category string. See [xcb-imdkit registration source](https://github.com/fcitx/xcb-imdkit/blob/master/src/imdkit.c#L2618-L2627) and [selection ownership source](https://github.com/fcitx/xcb-imdkit/blob/master/src/imdkit.c#L2637-L2754). The generated XRes accessor reports one decoded CARD32 for a wire `ClientIdValue.length` of four bytes; the C helper and no-display self-test check both representations.
4. The harness launches the private session host with a fresh journal and a private short IPC path, then starts a raw/no-echo Python PTY fixture. The child signals `READY` over a private Unix control socket and emits a terminal marker; it does not echo terminal input. The actual app runs without diagnostic/preedit fixture arguments. The app window must expose `_NET_WM_PID` matching the exact app PID and XRes must resolve the same XID to that PID; a missing window is a hard helper failure, and a `false` probe result is not accepted as readiness. GPUI gets only the private X11 `DISPLAY`; no Wayland, host D-Bus, host HOME, `ZED_HEADLESS`, or desktop token is inherited. Software rendering uses a privately remapped Lavapipe ICD; the source ICD hash and private mapping hash are recorded. The generated private passwd/group files contain root plus the invoking user's numeric uid/gid, matching the established isolated-render harness pattern.
5. The fixed-sequence helper has no arbitrary text/key input. It first verifies/focuses the exact app window using a separate `focus` stage with no XTEST calls, waits briefly for focus delivery, then the harness selects and activates Pinyin through private D-Bus and confirms the current IM name. Before each `compose` (`n i h a o`) or `commit` (Space) stage the helper revalidates the boot/PID/start identities for Xvfb, Fcitx and app, local socket inode and peer, XTEST, active XIM owner, app window, and private focus. Any mismatch fails before synthetic events. The helper links only X11/Xtst/XCB/XRes; it never addresses the host desktop. A bounded `XGetImage` capture writes a private P6 PPM from the Xvfb root, limited to 1280×800.
6. After the composition keys, the harness asks the PTY child to verify it received no bytes before Space and confirms host terminal output stayed unchanged. It captures that pre-commit screen for review. Space then causes the child to read exactly six UTF-8 bytes for `你好`, wait for extra/double bytes, and print a unique child-generated ACK only on an exact one-time match. The parent requires that ACK in a host frame. This tests the real XTEST → Fcitx Pinyin → XIM → GPUI → PTY path; it does not inject the expected Unicode directly, and no keyboard input is journaled. The report records the exact payload hash and byte count, not the payload as a journal entry. Screenshots are evidence to review, not a machine assertion that preedit was visible.

If an X window manager is needed for focus behavior, run a pinned minimal test WM inside the same namespace and SDK. Do not use host compositor focus controls. Prefer a direct, PID-verified `XSetInputFocus` helper if that is sufficient for GPUI; this choice must be validated against the actual app window rather than assumed.

## Hard preflight failures

Do not send even synthetic test keys if any of these hold: package signature/hash/path validation fails; XTEST is absent; Xvfb identity or socket ownership is ambiguous; the app window PID does not match; the helper resolves any display other than the private Xvfb; host display/session sockets or environment variables remain reachable; Fcitx uses inherited profile state; the XIM owner is not the private Fcitx process; or the network namespace has a usable external route. Do not retry with host display, host Fcitx, broader mounts, or a new display after an unknown launch outcome.

## Acceptance and limits

A pass would certify only that this exact built PigADE app, GPUI revision, Linux/X11/XIM backend, Fcitx/Pinyin package set, UTF-8 locale, Xvfb setup, and test sequence produced one `你好` commit in this isolated fixture. It would not certify Wayland text-input-v3, desktop-global behavior, other IMEs/layouts/locales, popup placement, caret/selection styling, reset/focus-loss barriers, or cross-machine determinism. The existing composition plan's reset-generation barrier remains a separate known product issue and is intentionally outside this test-plan slice.

The locale check is a specific go/no-go risk: GPUI's XIM open locale is `C`, while Fcitx's environment guidance warns against `C`/`POSIX` XIM locales. Fcitx's client-side locale-check omission is encouraging but insufficient. If the actual app does not receive a Unicode commit, first retain bounded evidence of XIM selection, open, preedit, and commit status. Do not manufacture success by bypassing XIM or writing Unicode directly to the host.
